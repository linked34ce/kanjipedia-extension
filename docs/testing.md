# テストの方針と全体点検

2026-11-17 JSTに、`tests/*.test.js` の全8ファイルと `tests/browser.js`、保存実HTMLの受入検証を点検した。変更前の53テストは成功したが、期待値の作り方、保存障害の再現、失敗理由の照合に改善点があった。修正後は96テストが成功している。件数の増加だけを品質の根拠にはしない。

## 判断の基準

t_wada氏の[現在時刻が関わるユニットテストから、テスト容易性設計を学ぶ](https://t-wada.hatenablog.jp/entry/design-for-testability)で説明される、再現可能性、テストの独立性、失敗原因の分かりやすさ、実装の変更に対する脆さを参考にした。以下は本プロジェクトでの適用判断であり、本人によるレビューや承認ではない。

- 入力条件と期待する結果を具体例で表す。リンク数だけでなく表示文字列・URL・原文、収集では送信要求・保存結果・再開後の状態を観測する。同じ仕様を説明する複数のassertはまとめてよい。
- 期待値は仕様や確認済みの受入例から決める。本番の候補選択関数やパーサーで正解を計算しない。順序を変えた入力から同じ辞書が得られる性質の検証は、具体的な期待内容の検証と組み合わせる。
- 時計・待機・乱数・HTTPは制御し、一時ファイル・モック・子プロセス・ブラウザは成功時も失敗時も後始末する。実際のファイル操作や複数プロセスを使う検証も、扱う境界に合わせて残す。
- 異常系は意図したエラー・終了コード・保存状態を確かめる。無関係なTypeErrorや入力の不足で通るテストにしない。条件を列挙するときはテスト名またはassertの説明から入力を識別できるようにする。
- 保存障害はファイルI/O境界で起こし、確定データの保持と再開結果を確認する。内部の関数分割や呼び出し回数自体を仕様にしない。HTTP要求回数は負荷制限・再取得禁止という外部の契約なので検証する。

## 対象ごとの結果

| 対象                   | 確認・改善した内容                                                                                                                                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `core.test.js`         | 正規化・URL安全性・辞書安定性・抽出・DOMを確認。候補照合に本番の辞書生成を使わない具体例を追加。同形異読、同一URLの複数読み、別URLの曖昧性を区別し、DOMのリンク先も照合。空本文・条件違い・重複URLなどは原因別に検証                                    |
| `http.test.js`         | 時計・待機・HTTP差し替えを継続。本文読了までの排他、応答完了後の間隔、日次499→500と翌UTC日、冷却期限の1ms前と期限ちょうど、再試行ジッター・既存の長い待機の維持、送信前の保存失敗を追加。拒否応答ごとの停止理由・応答保存も照合                         |
| `run.test.js`          | 同じ状態を異なる中断段階としていたケース名を修正。古い解析結果を保存本文から再解析する例と、HTML確定・done確定時の実際の保存失敗を追加。ディスクからrunを読み直して追加取得なしで再開できることを確認。矛盾検出・部分出力・完成世代保護の回帰試験は維持 |
| `store.test.js`        | 無関係なtmpファイルを置くだけの原子性確認を置換。writeFile・sync・renameの各障害後も確定ファイルが変わらず、その後に更新可能であることを検証。実プロセス4つのロック競合試験は維持                                                                       |
| `cli.test.js`          | 実際のCLI子プロセスでvalidateを検証。破損manifestでは終了コードだけでなくJSON解析エラーも確認                                                                                                                                                           |
| `review.test.js`       | 検索・記事それぞれの欠落、失敗応答、表記・読みの不一致、提案との不一致、両証跡の改変を独立したケースで検証                                                                                                                                              |
| `build.test.js`        | 特殊文字・プロトタイプキーの復元とMV3設定を確認。ハッシュ不一致時に既存生成物を変更しないことを別ケースで検証                                                                                                                                           |
| `package-data.test.js` | 公開manifestの内容と出力ファイル一覧を具体的に照合。ハッシュ不一致時に公開辞書・manifest・生成JSが変わらないことを検証                                                                                                                                  |
| `browser.js`           | 本番のchooseCandidateによる期待値計算を廃止。正しい白亜のURLを固定し、曖昧候補・読み不一致・未登録語を合成入力に含める。ユーザー操作前の要求一覧を比較し、遷移先URLへの通信も除外しない。Enter前後のタブ数も比較                                        |

ファイルを使う単体・結合テストは `tests/helpers/files.js` で作ったテスト専用ディレクトリを終了時に削除する。ブラウザ試験も一時プロファイルとビルド出力をfinallyで削除し、比較画像と結果だけを `artifacts/` に残す。

## 不具合を検出できることの確認

作業ツリーを変更しない `.local/` 内の別コピーで、次の改変を一度に1つずつ加え、対応するテストがアサーション失敗になることを確認した。これは選んだ8例の検出確認であり、全コードのmutation scoreではない。改変コードと一時コピーは公開対象に含めない。

| 意図的な改変                                 | 検出するテスト                     |
| -------------------------------------------- | ---------------------------------- |
| 単一URL制約を外し、複数URLから先頭を採用     | 候補照合の具体例                   |
| 複数読みの一部が未解決でも採用               | 読み不一致・複数読みの照合         |
| 日次上限の比較を `>=` から `>` に変更        | 500要求到達後の送信拒否            |
| 冷却期限の比較を `<` から `<=` に変更        | 冷却期限ちょうどからの再開         |
| 再試行予約の `Math.max` を `Math.min` に変更 | ジッター・長い待機の維持           |
| 一時ファイルの確定前に本ファイルを上書き     | 保存障害後の確定データ保持         |
| 応答一式より先にHTMLを保存                   | HTML保存失敗後の追加取得なしの再開 |
| リンク生成時に遷移先URLを余計にfetch         | ブラウザの操作前要求一覧の比較     |

最後の例は、従来のブラウザ試験では要求一覧から遷移先URLを一律除外していたため見逃し得た。現在は操作前に一覧を確定し、ユーザーのEnterによる遷移要求と分けている。

## 実行方法と限界

通常の実行手順は [開発手順](development.md#環境とオフライン検証)、今回実行した検証は [実装・受入検証](verification.md#テスト全体の点検と補強2026-11-17) を参照する。`node --test tests/http.test.js` のように対象別にも実行できる。

ブラウザ試験の既定の期待値は「亜の下つきで白亜だけが確認済みURLへリンクされる」という受入例。別の辞書・HTMLを試す場合は、確認済みの期待値をJSON配列として用意し、`--expected FILE` で渡す。各要素は `{ "text": "白亜(ハクア)", "href": "https://www.kanjipedia.jp/kotoba/0005614200" }` の形式とし、本番コードから生成しない。

保存障害の試験はI/O例外からの回復と保存済み状態からの再開を扱う。OSの強制終了・電源断・ファイルシステムの耐久性の保証ではない。HTTPのタイムアウト型障害は差し替えで再現し、30秒の実時間経過によるAbortSignal発火は試験していない。Chromiumの通信は遮断しており、実サイトを通常のChromeで開く手動目視は未実施。自動テストの成功を全入力の正しさや手動確認の代わりとは扱わない。
