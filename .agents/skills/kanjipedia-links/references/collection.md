# 収集・データ仕様

## 実装構成と段階

既存構成がなければNode.jsのサポート中LTSとJavaScriptを用い、HTMLパーサーはDOMを扱えるものを選ぶ。導入時のバージョンを固定する。推奨分離は `collector/`（HTTP、抽出、キュー）、`shared/`（正規化と照合）、`data/`（生成JSON）、`extension/`、`tests/fixtures/`。詳細は既存構成に合わせる。

CLIは調査、少数収集、再開、オフライン再解析、ビルド、検証を分ける。既定の収集上限は10リクエストとし、全体実行は明示的なモードにする。オフライン工程はネットワーク不要で動く。処理結果と終了コードで成功・未完了・停止理由を区別する。

最初に少数fixtureでパーサーを通す。次に「あ」の1・2・最終ページを少数調査し、重複や抜けを調べる。その後に全接頭辞を計画する。濁音の重複はURL集合で統合する。全件の個別記事巡回は行わず、曖昧な構造の代表例だけを追加確認する。

## レート制限と停止

以下は運営が保証する安全値ではなく、本プロジェクトの保守的な初期設定。robotsにより長い間隔があればそちらを優先する。

- ホスト全体で同時実行1。プロセスロックで二重起動を防止する。検索・robots・検証GET・リトライにも共通のゲートを使う。
- 通常の要求開始間隔は10秒以上＋0～5秒のジッター。前応答完了後にも10秒以上空ける。ヘッダーを正直に設定し、アクセス制限の回避やプロキシ切替は行わない。
- 通常モードの初期上限は1日500要求（失敗も含む）。上限と最終要求時刻、次回可能時刻を永続化し、再起動でリセットしない。日付はUTCで統一し記録する。
- タイムアウト30秒。ネットワーク障害・5xxは初回を含め最大3試行。待機は60秒、180秒＋ジッター。連続3失敗で実行全体を停止し、再開可能にする。
- 429ではRetry-Afterの秒数／HTTP日時を解釈し、最低15分または指定時刻の遅い方まで全体を停止する。日時が不正なら最低15分。冷却後の試行も上限内に数え、再429で停止する。
- 401・403・CAPTCHA・ブロック画面は即停止。HTMLの200応答でも構造不一致、条件違い、同じページの反復は止める。404や空本文を「0件」として保存しない。
- リダイレクトは上限3回、同一許可ホスト内のみ。各要求に間隔制限を適用する。未知ホストへ自動転送しない。

## 再開と証跡

キューは `(prefix, page, 検索条件, runId)` を主キーに、pending／inflight／done／failed、試行回数、応答状態、取得時刻、本文ハッシュ、保存先、抽出件数、解析器バージョンを保持する。SQLite等のトランザクションか原子的置換で破損を防ぐ。

成功本文を先に一時ファイルへ保存して確定し、解析・検証が通ってからdoneを記録する。クラッシュ後のinflightは本文ハッシュと保存状態を照合して回復し、取得済み本文があれば再解析する。Ctrl+Cでは状態を保存して終了。失敗ページを飛ばした実行は未完了とする。

HTMLとヘッダーはローカル調査用に保存し、公開リポジトリへ一括追加しない。Cookieや認証情報を保存しない。fixtureは必要最小限の構造断片または合成HTMLを使い、取得物と合成物を区別する。

再開時は既存runのキューを使う。更新は新runを作り、途中で古い世代と混ぜない。新runが完全で検証済みになるまで公開用JSONを置き換えない。

## 巡回と完全性

接頭辞一覧を設定として保存する。通常のひらがなに加え、濁音・半濁音・歴史的仮名・小書き文字等を「検証済み／対象／不要の根拠／未確認」で管理する。清音に含まれるか未確認の接頭辞を勝手に対象外にしない。

最初の正常ページから総件数、ページ件数、最終ページ候補を取り、ページ1～末尾を明示キュー化する。URLのpage省略は内部で1へ正規化する。pagerの範囲が途中まででも末尾を取り逃さない。現在ページと要求ページの不一致、重複本文ハッシュ、項目数の過不足を検知する。

0件は正常な検索条件表示と0件表示を検証して初めて確定する。件数変動が出たら影響する接頭辞を未完了にし、上限内で別世代として取り直す。無限に再巡回しない。

接頭辞ごとに総件数、ページ数、取得行数、固有URL数、重複件数、欠落ページを報告する。接頭辞間で同じURLが現れることは正常な重複として統合できる。結果行総数と固有URL数を混同しない。完全性は「検証した検索接頭辞の範囲」について述べる。

## 見出しと正規化

`#resultKotobaList` 内のリンクだけを抽出し、アンカーの最初のbrより前を見出し、後ろの読みspanを読みとして扱う。無関係なリンクや広告は拾わない。URLは同一オリジンの `/kotoba/[0-9]{10,11}` のみ許可し、相対パスに統一する。2026-11-17に11桁の瞳睛 `/kotoba/00007484700` がHTTP 200で正しい見出し・読みを返すことを追加確認した。桁数を無制限に許可せず、期待外の構造は診断へ送る。

原表記と原読みを保存したうえで照合キーを別に作る。見出しのsup内にある▲△は注記として除去し、〈〉は表記を囲む記号として除去する。文字としての中点は機械的に全分割しない。異表記区切りと確認できる中点だけを分割し、未確定例を診断へ残す。

前後空白、確認済み注記、囲み記号以外を無条件に消さない。互換漢字、異体字、旧字体、IVSを一律NFKCで潰さない。読みは括弧を除去し、ひらがな／カタカナを同一形式へ揃える。小書き、濁点、長音、送り仮名の区切りは根拠のない同一化を避ける。合成濁点の正規化は読みだけに適用しテストする。解釈不能な画像をaltから漢字として推測しない。

## JSON契約

単純な語→単一URLでは同形異読を失うため、配列を正規形式にする。以下は確認済みの愛着2項目による契約例。`generatedAt` 等のビルドメタデータは別manifestに保存する。

```json
{
  "schemaVersion": 1,
  "entries": {
    "愛着": [
      { "path": "/kotoba/0000021500", "reading": "アイジャク" },
      { "path": "/kotoba/0000023100", "reading": "アイチャク" }
    ]
  }
}
```

内部recordsはpath、rawHeading、rawReading、variants、正規化済みreading、出典の検索URL・ページ・取得時刻・本文ハッシュを保持する。同じvariant／reading／pathは集合として統合する。異なるURLは上書きしない。同一URLで見出しや読みが矛盾したら診断を残す。

生成はキー、候補を固定順に並べ、UTF-8、安定した改行で出力する。時刻を含まない辞書本体は同じ入力から同じバイト列にする。manifestに辞書SHA-256、runId、スキーマ・解析器バージョン、収集期間、接頭辞範囲、欠落・衝突・未解釈件数とcompleteを記録する。JSON Schemaで型、必須項目、path形式を検証する。`__proto__` 等のキーにも安全なMapまたはown-property参照を使う。

語が見つからないことを「辞典に存在しない」と断言しない。収集不足・未解釈との区別を保持する。実行時の検索や不存在キャッシュは必要ない。
