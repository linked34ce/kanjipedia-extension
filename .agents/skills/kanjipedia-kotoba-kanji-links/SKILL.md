# 漢字ペディア 言葉見出しから各漢字へのリンク

対象は `C:\Users\9797o\Programming\kanjipedia-extension`。言葉個別ページの大きい見出しにある漢字を一字ずつリンクにする。例は [螺旋](https://www.kanjipedia.jp/kotoba/0007016000) で、「螺」と「旋」をそれぞれ確認済みの漢字個別ページへ移動できるようにする。

このSkillは追加機能の実装方針であり、機能や漢字対応表の実装済みを意味しない。方針の作成・更新だけを依頼された場合はSkillの編集に留め、拡張や収集処理を変更・起動しない。後に実装を依頼された際は以下の方針に沿って作業する。

## 機能の範囲

- 対象URLは `https://www.kanjipedia.jp/kotoba/[0-9]{10}`。大きい見出しの漢字だけを一字ずつリンク化し、読み・説明文・関連語・ページ上部の別見出しは保つ。
- 語の表記を変えず、注記の▲△、囲み記号、中点、送り仮名、空白、外字画像も保つ。同梱データで一意に決められる文字だけを変更する。
- 拡張の実行中は外部検索や取得を行わない。漢字→漢字ページURLの静的対応表を事前に作り、ビルド時に同梱する。
- 既存の「下つき」補完と併存させる。下つきは語・読み全体、言葉の見出しは漢字一字ずつという単位の違いを保持する。
- 公開先はGitHubのみ。最小限の対応表と生成済み拡張を配布し、生HTML・HTTP証跡・キューを公開しない。Chromeウェブストアへは申請しない。

## 作業方針

1. 親ディレクトリを含む `AGENTS.md` と、`extension/source.js`、`manifest.json`、`content.css`、`scripts/build.js`、`scripts/package-data.js`、既存テストを読む。既存の機能・辞書・公開済みファイルを尊重する。
2. [調査記録と未確認事項](references/site-findings.md)を読む。螺旋の生HTML・大見出しのDOM・既存の先頭漢字リンク・漢字検索結果を少数アクセスで確認する。候補セレクターを確認済み事実として扱わず、螺・旋のURLの数値IDを推測しない。
3. [実装・データ・検証計画](references/implementation-plan.md)に従い、まず合成fixtureで漢字対応表、Unicode文字の扱い、DOM範囲の書換えを実装してオフライン検証する。
4. 収集は既存の `HttpGate` とプロセスロック・永続カウンターを共用する。新しい漢字収集runを既存の言葉収集runと分け、検索の種類・条件を明示する。日次枠がない間は追加のサイト取得をせず、保存資料とfixtureで進める。
5. 対応表は「螺」「旋」の少数検証から始める。全体収集へ広げるときは、漢字の読み検索など検索結果からまとめて取得できる方式を検証し、全言葉記事の巡回や文字ごとの大量検索を避ける。
6. MV3の対象に言葉ページを追加し、既存ページとは処理を分ける。注入する同梱JSとCSSをビルド・公開用パッケージに含め、ネットワーク不要で動くことを確認する。
7. fixtureと保存実HTMLで受入検証し、実機の手動確認は実施・未実施を分けて記録する。READMEには導入・仕様・使い方だけを更新し、調査や収集範囲はdocsへ書く。意味のある作業単位ごとに検証してコミットする。

## 完了の基準

- 検証した螺旋ページの大見出しで「螺」「旋」が別々のアンカーとなり、それぞれ確認済みURLへ同一タブで移動できる。
- 大きい文字のフォント・字形・文字列・行高を保ち、既存と調和する淡い青色のリンク表示とキーボード操作を確認できる。
- 未登録文字、曖昧なURL、異体字・IVSの未対応、未知のマークアップは原文を保ち、二重リンクや文字化けを作らない。
- 下つき機能の既存テストが通り、両機能を実際に読み込んだChromiumで拡張由来の追加HTTPが0件となる。
- コード完成、対応表の収集範囲、解析保留、実サイトの手動確認を別々に報告する。部分対応を全漢字対応と呼ばない。
