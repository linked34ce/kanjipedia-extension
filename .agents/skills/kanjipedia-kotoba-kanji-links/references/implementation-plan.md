# 実装・データ・検証計画

## 漢字対応表

既存の辞書は表記・読み→`/kotoba/` の候補であり、漢字個別ページのURLは導出できない。漢字→`/kanji/` の対応表を別のJSON原本として管理する。既存の `safePath` は言葉用なので、漢字用のURL検証を分け、既存の許可範囲を広げない。

契約は `schemaVersion` と `entries` を持ち、キーは確認済みの漢字1文字分の書記素、値は `{ path }` の候補配列とする。以下は保存資料にある「白」のリンクによる例で、螺・旋のID例ではない。

```json
{
  "schemaVersion": 1,
  "entries": {
    "白": [{ "path": "/kanji/0005607600" }]
  }
}
```

- URLは同一オリジンの `/kanji/[0-9]{10}` のみ許可し、クエリー・フラグメント・認証情報を認めず相対パスに統一する。
- 候補の同一URLは集合として統合し、異なるURLは上書きしない。同じ文字に複数URLが残ればリンク化を保留する。
- 文字のキーにNFKCやNFCを一律適用せず、旧字体・互換漢字・IVSを区別する。通常字のURLを異体字やIVS付き文字へ自動流用しない。
- 取得元URL、取得日時、本文ハッシュ、原表示、保留理由はローカルrecordsに保存する。公開用JSONは最小限の文字とURLだけにする。
- JSON Schema、安定順・UTF-8・改行、辞書SHA-256、収集範囲・欠落・衝突・解析保留・completeを持つ別manifestを用意する。Mapまたはown-property参照でキーを扱う。

## 収集と再開

初期検証は「螺」「旋」を含む小規模な対応表で行う。収集済みの言葉の表記から漢字候補を重複除去して抽出することはできるが、その表記一覧だけでは漢字URLの根拠にはならない。また、既存の言葉辞書から抽出した文字の範囲を全漢字とは呼ばない。

全体収集の第一候補は、サイトの漢字の読み検索等から検索結果をまとめて取得する方式。接頭辞の音訓・濁音・歴史的仮名の範囲とページャーを検証してから採用する。漢字一字の完全一致検索は少数の検証や未解決文字の補完に使い、最初から全文字を1要求ずつ検索しない。

`collector/http.js` と `collector/store.js` の共通ゲート・ロック・原子的保存を利用する。検索種別と条件を扱える抽出アダプター／キューを設け、既存の `wy=1`、言葉リストのセレクター、件数表示を漢字検索へそのまま流用しない。漢字収集は専用runとして分離し、既存の言葉収集runを変更・再取得しない。種別・検索条件・接頭辞または文字・ページ・runIdをキュー識別に含める。

既存の同時実行1、通常10要求上限、応答完了後10秒以上＋ジッター、UTC日次500要求、robots、429・401・403・ブロック時の停止、最大3試行を維持する。正常な0件表示を確認する前に空本文や404を0件にしない。検索条件違い、ページ反復、件数変動で停止し、取得済み本文は再解析して再利用する。漢字と語のデータを更新しても共有カウンターは維持する。

## 見出しのDOM処理

既存の `linkDocument` は漢字ページ専用なので、言葉ページ用の独立した関数を追加する。URLの厳密な検証後に、実HTMLで確認した大見出しを単一に特定する。複数候補や構造不一致ならそのページは変更しない。

文字列全体の置換は行わず、対象見出しのテキストノードに対して次を行う。

1. `Intl.Segmenter` のgrapheme単位などで、サロゲートペアや基底漢字＋異体字セレクターを壊さず文字の範囲を取る。DOM Rangeに渡す位置はUTF-16オフセットとして扱う。
2. 漢字として確認済みの書記素と対応表を完全一致で照合し、単一URLの場合だけリンクにする。かな・数字・句読点・々等の記号を近くの漢字に読み替えない。同じ漢字の繰り返しは出現箇所ごとに扱う。
3. 後ろの範囲からDOM Rangeでアンカーに包む。注記sup、読み、既存aの内部、既に追加したリンクを除外する。既存要素・イベント・テキストを保つ。
4. 外字画像のaltやファイル名から漢字を推定しない。ruby等の未確認構造や分割不能な文字は保留し、扱えることがfixtureで確認できた構造だけを追加対応する。

サイドバーの先頭漢字リンクは調査時の照合根拠に使えるが、未登録の2文字目以降を推測する根拠にはしない。本文・ページ全体のinnerHTML再代入や広範囲なテキスト検索置換は行わない。

## 拡張と配布物

- `manifest.json` の静的content_scriptsに `https://www.kanjipedia.jp/kotoba/*` を追加し、実行時にも数値10～11桁の言葉パスを検証する。document_idle、全フレーム注入なしを維持する。
- データJS→処理JSの順序とisolated worldを維持する。共通エントリーでURLごとに分岐するか、機能別スクリプトに分けるかは辞書サイズと既存構成で決める。両方の大きな辞書を全ページで不要に初期化しない。
- 漢字対応表はJSON原本から安全にシリアライズして生成する。通信や追加権限が不要な構成を優先し、eval、外部検索、履歴送信を追加しない。
- 漢字リンクに専用マーカーと限定したCSSを使い、親の大きいフォントサイズ・書体・太さ・行高・文字色を保つ。既存の淡い青色ハイライト、ホバー・focus-visibleを流用し、字間を変える余白や縮小表示を足さない。
- `scripts/build.js`、`scripts/package-data.js` と同梱manifestを更新し、元の言葉辞書と新しい漢字対応表をそれぞれハッシュ検証する。GitHubのZIPから追加収集なしで両機能を読み込める状態にする。

## テストの品質

既存機能の [テストの方針と全体点検](../../../../docs/testing.md) と、[下つき機能のテスト方針](../../kanjipedia-links/references/extension-and-tests.md#テストの品質) を追加機能にも適用する。螺・旋の期待リンクは確認済み資料から個別に指定し、本番のURL選択関数や書記素分割関数から正解を作らない。Unicodeの試験では文字列・URL・保持される要素を観測し、内部ヘルパーの分割方法を固定しない。追加HTTPの比較から遷移先を除外せず、保存復元の想定状態とI/O失敗の再現は区別して記録する。

## 検証とコミットの区切り

| 段階 | 必要な検証 |
| --- | --- |
| 調査・対応表の契約 | 螺旋の対象DOM、螺・旋の正しいURL、漢字検索の条件・表示を確認。未確認事項を記録 |
| 抽出・キュー・辞書 | 合成検索HTMLで抽出・0件・構造不一致・重複・衝突・危険URL・再開・安定生成・スキーマ不一致を検証。時計・HTTPを差し替えて実サイトや実待機に依存しない |
| DOMと見た目 | 螺旋の2文字が別リンク、同じ漢字の反復、送り仮名・複数表記・注記sup、未登録字、同字複数URL、既存a、外字画像、未知の入れ子、対象なし、2回実行をfixtureで検証 |
| Unicode | 補助平面の漢字、互換漢字、旧字体、基底字＋IVSを検証。未対応は保留し、文字やセレクターを分断しない |
| ブラウザ | Chromiumに実拡張をロードし、通信を遮断したルーティングで言葉ページと漢字ページを検証。各文字のクリック・Tab/Enter・同一タブ遷移、見出しの表示と他の欄の保持、例外0・追加HTTP0を比較。辞書サイズ・初期化・処理時間も記録 |
| 回帰・公開物 | 既存の下つきテスト、両辞書のハッシュ、クリーンなチェックアウトからのビルド再現と拡張読込を確認。取得HTMLやキューの非混入を確認 |

必要な単位で検証してコミットし、大量の収集データと機能変更を一括コミットにしない。実サイトの手動目視は少数ページに限定し、実施していない場合は未実施と報告する。見出しリンクの完成と対応表の収集完成を分けて記録する。
